靶场实操全记录

环境：本地靶场 http://localhost:3000（只监听 127.0.0.1） ·  7 关全部打通  ·  全部请求可在自己机器上复现

1 弱口令 ✅ 2 SQL 注入 ✅ 3 越权 IDOR ✅ 4 金额篡改 ✅ 5 反射型 XSS ✅ 6 存储型 XSS ✅ 7 敏感文件泄露 ✅

这份记录不是"答案清单"，而是一次完整测试的过程还原：每一步我是怎么想的、发了什么请求、服务端回了什么、从哪个细节判断出下一步该试什么。把 7 关串起来看，你会发现它其实是一个标准渗透测试项目的缩影——先侦察，再逐点测试，最后回到报告。

阶段一信息收集：先把"地图"画出来

新手最常犯的错误是一上来就往登录框里输密码。老手先花时间看。这一步在整个项目里占的时间最多，收益也最大——本次实操里，第 7 关的答案在这一步就已经暴露了。

动作 1：把首页暴露的入口全部抓下来

# 只抓"入口：xxx"这一行的路径，不猜，直接提取
curl -sS --noproxy '*' http://127.0.0.1:3000/ | grep -oE '入口：<code>[^<]*'

/login
/user?id=1
/orders
/shop
/search?q=hi
/guestbook
/robots.txt

7 个入口 = 7 个功能点。每个功能点后面都要问一遍"四个方向"，这就是后面的测试清单。

动作 2：先看 robots.txt —— 它是"此地无银三百两"

GET /robots.txt

User-agent: *
Disallow: /backup/
Disallow: /admin/
为什么先看它：robots.txt 的用途是"告诉搜索引擎别抓这些目录"，但它的内容对所有人公开。它等于站方主动写了一份「这里有些东西我不想让人看见」的清单。Disallow 的路径历来是目录爆破字典里最该优先试的一批。

动作 3：逐路径探测，看状态码

for path in /admin/ /backup/ /backup/config.bak /index.php /api/order /debug; do
  printf "  %-22s HTTP %s\n" "$path" "$(curl -sS --noproxy '*' -o /dev/null -w '%{http_code}' "http://127.0.0.1:3000$path")"
done

  /admin/                HTTP 404
  /backup/               HTTP 404
  /backup/config.bak     HTTP 200   ← 目录本身没开列表，但里面的文件能直接下
  /index.php             HTTP 404
  /api/order             HTTP 200
  /debug                 HTTP 404
这里有个关键认知：/backup/ 返回 404 不代表里面没东西，只代表"这个目录不允许列文件"。真正的探测要一路试到具体文件名。真实世界里 .bak .zip .git .svn .env config.php~ 都是同一批字典。
注意：状态码只是提示，不是结论——真正判定要去看返回内容里有没有敏感信息。

到此为止，一次请求都还没"攻击"过，但已经锁定了一条高价值线索。先拿这条，后面再回来收。

阶段二逐关测试：每一关都是一次"四个方向"的验证

01

弱口令登录

过度信任？不，是配置失误成因：人为疏忽

入口 /login。这类点位的思路不是"爆破一万次"，而是先试少数几个高频组合：admin/123456、admin/admin、admin/88888888、admin/admin123。

# 第一次：admin / 123456 —— 失败
curl -sS -i --noproxy '*' -X POST -d "username=admin&password=123456" http://127.0.0.1:3000/login | head -3

HTTP/1.1 302 Found
Location: /login?msg=fail       ← 302 跳回带 fail 的地址 = 失败

# 第二次：admin / admin123 —— 成功
curl -sS --noproxy '*' -X POST -d "username=admin&password=admin123" http://127.0.0.1:3000/login | grep -oE "FLAG\{[^}]*\}|登录成功"

登录成功
FLAG{n0_m0re_123456}
一个被低估的技巧：不要只看页面文字，要看响应头。这次登录失败返回的是 302 → /login?msg=fail，而成功是 200 直接渲染新页面。状态码和跳转地址本身就是最干净的判断信号，比去页面里找"用户名或密码错误"这行字可靠得多。真实测试里还可以看响应长度差异。
修复建议：① 禁止默认口令，首次登录强制改密；② 登录失败做次数限制 + 指数退避，防撞库；③ 管理后台不要暴露在公网，或加 IP 白名单 / VPN；④ 接入多因素认证。

合规提醒真实平台基本都禁止对登录接口做批量爆破（会锁账号，也违反测试规则）。弱口令只试少数几个高频组合，试不出来就放弃这个方向。

02

SQL 注入

改值 / 改类型成因：把数据当成了代码

入口 /user?id=1。靶场很贴心地把服务端执行的 SQL 打印出来了，但真实环境中没有这个福利，所以我们还是按真实流程走一遍：先正常请求 → 加一个单引号探测 → 根据反应判断。

第 1 步：先建立一个"正常"的基准。

GET /user?id=1

服务端实际执行的语句：SELECT * FROM users WHERE id = 1
id | 用户名 | 角色     | 备注
1  | alice  | 普通用户 | 我的生日是 1998-03-12

记住这个"正常长什么样"，后面所有异常才有对照物。

第 2 步：加一个单引号 —— 这是判断注入存在的经典手法。

GET /user?id=1'

服务端实际执行的语句：SELECT * FROM users WHERE id = 1'
SQL 语法错误：Invalid or unexpected token
这一步是整个漏洞的"定罪证据"。我只是输入了一个普通字符 '，应用却报了 SQL 语法错误——这说明：这个引号没有被当成"数据"，而是被塞进了数据库语句里，改变了语句的结构。一个字符就能让程序报错，等于应用亲口承认"我把你的输入拼进 SQL 了"。

真实的报错页面还会泄露更多：数据库类型（MySQL/PostgreSQL）、版本号、表的字段名、甚至服务器物理路径。报错信息本身就是情报，这也是为什么正式环境必须关闭详细报错。

第 3 步：既然值我说了算，那就构造一个恒真条件。

GET /user?id=1%20OR%201=1

服务端实际执行的语句：SELECT * FROM users WHERE id = 1 OR 1=1

查询结果：
1  | alice  | 普通用户 | 我的生日是 1998-03-12
2  | admin  | 管理员   | FLAG{sql1_str1ng_c0nc4t_w1ns}
3  | bob    | 普通用户 | 我的手机是 138****1234
原理：原本的语句是"取 id = 1 的那一行"。我加上 OR 1=1 之后，条件变成"id = 1 或者 恒真"——恒真意味着没有任何一行能被排除，于是整张表被吐了出来。

看清楚了：我没有猜密码，也没有破解任何加密，我只是把一个"条件"改成了它永远成立。这就是注入类漏洞的共同本质——控制查询逻辑，而不是破解凭据。
修复建议：① 用参数化查询（预编译语句）——这是唯一彻底的方案，让 SQL 结构在拼接前就固定下来，用户输入只能当值；② 对 id 这类参数做类型强校验（必须是整数）；③ 数据库账号最小权限，去掉不必要的读表权限；④ 生产环境关闭详细报错，统一返回泛化错误页。

合规底线真实测试中，SQL 注入只能取到证明漏洞存在所需的最小信息（库名、表名、字段名即可）。严禁 dump 用户数据、严禁改删数据。这是资质会被吊销、甚至要负刑责的红线。

03

越权访问（IDOR）

改身份 ← 新手最容易出成果成因：只认参数，不认人

入口 /api/order?id=1001。先看自己的订单建立基准：

GET /api/order?id=1001

商品：机械键盘  金额：¥399  说明：这是你自己的订单

确认了 URL 里的 id 就是订单编号之后，问自己那句核心的话："这个 id 我说了算吗？换成别人的会怎样？"

GET /api/order?id=1002

商品：显示器  金额：¥1899  说明：这是别人的订单
FLAG{1d0r_ch4nge_the_1d}
这类漏洞为什么值得你优先找：它几乎不需要任何"技术技巧"——不改包、不注入、不绕过滤器，只把数字改了一个。但它造成的后果可能是"任意用户可查看他人订单/资料/身份证照片"。

它之所以普遍，是因为开发时常常只写了"根据 id 查数据"，而忘了补一句"这个 id 属不属于当前登录的人"。功能测试时用管理员账号走一遍全都正常，所以最容易漏。

要试的参数名远不止 id：uid、userId、orderId、accountId、fileId、docId、tenantId、role……
修复建议：① 服务端从会话（Token/Session）里取当前用户身份，而不是从请求参数里取；② 每次访问对象前做归属校验（WHERE id = ? AND owner_id = 当前用户）；③ 用不可枚举的随机标识（UUID）替代自增 ID，提高遍历成本（这只是缓解，不能替代授权校验）。
04

金额篡改（业务逻辑漏洞）

改顺序 / 改值成因：过度信任客户端

入口 /shop。商品标价 ¥399。观察下单表单：金额是浏览器提交上来的一个字段——这就是破绽。

# 先用原价走一遍，确认流程正常
curl -sS --noproxy '*' -X POST -d "item=机械键盘&amount=399" http://127.0.0.1:3000/api/pay | grep -oE "下单成功[^<]*"

下单成功：机械键盘，实付 ¥399

# 再只改一个字段的值（商品不动）
curl -sS --noproxy '*' -X POST -d "item=机械键盘&amount=0.01" http://127.0.0.1:3000/api/pay | grep -oE "下单成功[^<]*|FLAG\{[^}]*\}"

下单成功：机械键盘，实付 ¥0.01
FLAG{trust_n0_client_4mount}
关键点：改的是"服务端本不该听的那个字段"。商品是真货、页面没改过、请求也没伪造——我只是如实告诉服务端"你收 0.01 就行"，而它信了。

真实世界里这个字段可能叫 amount、price、total、discount、quantity、couponId。判断标准只有一句话：这个值如果被客户端随意指定，会不会造成资金损失？

同类的还有：把数量改成 -1（退款叠加）、重复使用同一张优惠券、跳过支付直接访问"支付成功"回调、把订单状态直接改成"已发货"。这类洞不需要技术，需要的是商业理解。
修复建议：① 价格、折扣、总金额全部由服务端根据商品 ID 自己计算，客户端只传"买了什么、买几个"；② 对金额做区间与一致性校验；③ 支付回调必须验签，且幂等；④ 关键业务操作（下单、退款、提现）必须做服务端状态机校验，不允许跨状态跳转。
05

反射型 XSS

改值 / 改类型成因：输出未编码

入口 /search?q=hello。第一步永远是：先确认输入会不会被原样显示在页面上。

GET /search?q=hello
关键词：<b>hello</b>

# 换成一段带标签的内容，看它被"当文字"还是"当代码"
GET /search?q=%3Cb%3Etest%3C%2Fb%3E
关键词：<b><b>test</b></b>       ← 我输入的 <b> 没被转义，直接变成了加粗标签

# 既然标签能生效，换成 script 试试
GET /search?q=%3Cscript%3Ealert(1)%3C%2Fscript%3E
FLAG{reflected_xss_1s_y0urs}
推理链条是这样的：
① 我输入 <b>test</b>，页面返回的 HTML 里原样是我的 <b>，而不是 &lt;b&gt;；
② 说明服务端没有对输出做 HTML 编码；
③ 那么浏览器在渲染这段 HTML 时，会把我写的东西当成页面结构的一部分而不是文字；
④ 于是把 <b> 换成 <script>，浏览器就会执行它。

这一步是一次"等价替换"，不是撞运气。真正的危害不在 alert(1)，而在于攻击者可以构造一个链接，让受害者点开后在其浏览器里以受害者的身份执行任意操作——这就是"窃取登录态（Cookie）"的经典路径。
一个必须讲清楚的技术细节：我用 curl 只能证明"服务端把 <script> 原样吐回来了"，但 curl 不会执行 JavaScript。
要证明"真的弹窗了"，必须用浏览器打开这个链接亲眼看。这就是为什么 XSS 类漏洞的报告里必须有一张浏览器截图——光有 HTTP 响应，审核人员会怀疑你是不是把"回显"当成了"执行"。
修复建议：① 输出的时候按上下文转义（HTML 正文转义 & < > " '）；② 优先用框架自带的安全输出（Vue/React 默认转义，别随便用 v-html / dangerouslySetInnerHTML）；③ 配合 CSP（内容安全策略）作为纵深防御；④ Cookie 加 HttpOnly，即使被 XSS 也偷不到会话。
06

存储型 XSS

改值成因：输入未过滤 + 输出未编码

入口 /guestbook。反射型是"谁点链接谁中招"，存储型是"所有访问者都中招"——区别就在于内容是永久存在服务端的。

# 提交一条带事件的留言
curl -sS -X POST --noproxy '*' \
  --data-urlencode "user=attacker" \
  --data-urlencode "text=<img src=x onerror=alert(document.cookie)>" \
  http://127.0.0.1:3000/guestbook -o /dev/null -w "提交 HTTP %{http_code}\n"

提交 HTTP 302   ← 302 = 保存成功并跳回列表

# 关键：以"另一个访客"的身份重新打开留言板（不带你刚才的输入）
curl -sS --noproxy '*' http://127.0.0.1:3000/guestbook | grep -oE "onerror=alert[^>]*"

onerror=alert(document.cookie)
FLAG{stored_xss_h1ts_everyone}
注意我刻意用了 <img onerror=> 而不是 <script>。这来自一个真实世界的重要经验：现代浏览器在插入 innerHTML 时默认不执行 <script>，但会执行 onerror、onload 这类事件属性。换一种"等价但更可能生效"的写法，是测试中非常常见的思路——同一个目标，多试几种载体。

另外注意：我是用第二次请求去读留言板的。第一次是"写入"，第二次是"读取"。这个"写入 → 换个身份重新读取"的动作，就是验证存储型 XSS 的标准姿势——它证明了恶意内容已经进入了服务端、并对所有人可见。
修复建议：① 存储前做白名单过滤，输出时按上下文编码（两者都要，不能只做一半）；② 富文本场景用专业库（DOMPurify）做净化，而不是自己写正则；③ 全站开启 CSP，限制内联脚本与外部域加载。
07

敏感文件泄露

改值（路径）成因：部署疏忽

这一关的答案在阶段一就已经拿到了。当时侦察发现 /backup/config.bak 返回 200，现在回来收它：

GET /backup/config.bak

# 站点备份配置 —— 本该永远不放在公网
DB_HOST=127.0.0.1
DB_USER=root
DB_PASS=FLAG{b4ckup_f1les_4re_g0ld}
SECRET_KEY=9f3a2b7c1e8d
为什么这个洞比看起来严重得多：拿到这里的数据库账号密码之后，攻击者往往不需要再挖任何 Web 漏洞——直接连数据库就行了。同理还有 .git/config（能还原整站源码）、.env（各种密钥）、web.config.bak、备份的 SQL 文件。

习惯养成：看到 robots.txt 里的 Disallow 路径，先按目录探，再按"常见备份文件名"探——index.php.bak、www.zip、backup.tar.gz、.DS_Store。这一步在真实项目里产出率很高，而且技术门槛低。
修复建议：① 备份文件、源码包、配置文件一律放在 Web 根目录之外，或改用对象存储 + 鉴权下载；② Nginx/Apache 显式拒绝对 .bak .zip .sql .git .env 等后缀的访问；③ 立刻轮换已泄露的密钥与数据库口令（已泄露的凭据不能只删文件就算修好）；④ 上线前用"发布检查清单"扫一遍根目录。

阶段三收尾：把测试过程变成一份能提交的报告

挖到漏洞只完成了工作的一半。在 SRC/众测平台上，"漏洞能不能过审、能定几级"，很大程度取决于报告写得怎么样。下面是第 2 关 SQL 注入的标准报告形态，可以直接当模板用。

字段内容
漏洞名称用户查询接口存在 SQL 注入
漏洞类型SQL 注入（OWASP A03:2021 注入类）
危害等级高危
漏洞 URLhttp://host/user?id=1 ← 必须给完整 URL，含参数
漏洞参数id（GET）
复现步骤1. 访问 /user?id=1，正常返回用户 alice 的信息
2. 在 id 后加入单引号 /user?id=1'，页面返回 SQL 语法错误
3. 构造 /user?id=1 OR 1=1，返回全部 3 条用户记录
4. 证明 payload 改变了查询条件结构，属注入
危害说明攻击者可绕过查询条件读取数据库中任意数据；若数据库账号权限过高，进一步可能读取服务器文件、写入文件获取服务器权限。当前实际影响：可越权读取全部用户记录。
修复建议使用参数化查询（预编译）；对 id 做强类型校验；生产环境关闭详细报错；数据库账号最小权限。
附件① 正常返回截图 ② 单引号报错截图 ③ OR 1=1 返回全量数据截图 ④ 原始请求包
四个最常见的驳回原因，直接决定你能不能拿到钱：
1. 截图不清晰，或截图里看不到完整 URL —— 审核员无法确认你打的是哪个资产；
2. 没有给完整 URL / 参数，只说"用户查询页面有注入"；
3. 危害等级定错（把信息泄露报成高危，或者把 SQL 注入报成低危）；
4. 修复建议空泛，只写"建议加强安全防护"。

报告里每一条都要能被别人照着复现一遍——这是唯一的验收标准。

复盘：这 7 关真正教你的是什么

把 7 关按"四个方向"重新排一遍，你会发现它们不是 7 个孤立的知识点，而是同一个提问框架的 7 次应用：

方向要问自己的那句话本次命中
改值这个参数我说了算吗？改成 0 / -1 / 超大数 / 特殊字符 / 超长串会怎样？SQL 注入（加 OR 1=1）、金额篡改（399 → 0.01）、XSS（塞标签）、文件泄露（换路径）
改身份把 id / uid / orderId / role 换成别人的或管理员的，还能访问吗？越权 IDOR（1001 → 1002）
改顺序该三步走的流程能不能跳到第三步？重复提交、并发提交会怎样？金额篡改里"价格本该服务端定"就是同一类问题
改类型数字换字符串、false 改 true、删字段、多传字段？SQL 注入（引号改变类型）、XSS（文字 → 代码）

还有三条比技术更重要的东西，值得写下来：

  • 先看，再打。本次第 7 关在侦察阶段就解决了；真实的项目里，信息收集通常占掉七成时间。急着输密码、急着丢扫描器，是最典型的低效。
  • 报错和状态码是免费情报。一个引号换来一句 SQL 报错、一次 302 跳转暴露登录成败、一个 200 暴露备份文件——这些都是"应用自己说漏嘴"，比你去猜可靠得多。
  • 同一个目标多试几种载体。XSS 里 <script> 不行就换 <img onerror>，真实环境里浏览器和 WAF 的拦截规则各不相同，会变通的人才挖得到洞。
最后，那条唯一不能越过的线：
本次实操里所有的"攻击"动作，之所以随便发都合法，只因为这个靶场是你自己的。
真实系统上，没有明确授权，发出去的第一个包就是违法行为（非法侵入计算机信息系统）；拿漏洞向企业索要钱财，属于敲诈勒索，不是漏洞赏金。
合法的真实战场只有一条入口：平台明确列出的授权范围（scope）内。靶场里你怎么打都行，出了靶场，先看授权。
